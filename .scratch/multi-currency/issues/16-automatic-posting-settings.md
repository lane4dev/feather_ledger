# 三类账单的自动处理设置如何工作
Type: grilling
Label: wayfinder:grilling
Status: resolved
Assignee: codex
Blocked by: 03

## Question

设置中分别控制订阅、计划交易和重复交易的自动入账。开关变化对逾期账单、实际触发时机、提醒及新账单模式如何生效？

## Context

现有应用不连接银行，也不执行真实支付。当前只有订阅系列使用 `autoPost`；计划是一次性系列，重复系列与订阅共享模型但通常不自动入账。用户要求在新模型持久化创建时的模式，并明确不要求兼容旧数据。三个开关为本机设置，不纳入备份；账单资格和待确认批次需覆盖备份与恢复。

用户已确认暂停期间到期的旧实例、以及切换离开时已到期未记入的实例，切回后始终等待手动处理，单期改期不改变资格。

## Comments

- 用户确认：“自动支付”指非默认模式（计划、订阅、重复）的收支在到期后自动记入账本；不涉及银行或真实扣款。领域术语使用 Automatic posting（自动入账）。
- 用户确认：三个开关全局控制各类型已有和未来账单；因暂停币种而转为手动处理的实例仍须手动，开关不能覆盖这项决定。
- 用户确认：三个开关初始默认全部关闭。现有代码中的订阅原本在应用启动时会自动入账，新模型行为与之不同；用户已排除对新模型上线前数据的兼容。
- 用户确认：开关关闭期间到期的账单仍须手动处理；之后打开开关只自动处理开启后到期的账单，不追溯补记旧账单。
- 用户确认：沿用启动时机制；账单到期时即使应用正在前台，也在下次打开应用时自动记入，不新增后台到点自动入账。
- 代码核对：当前 `AccountService.restoreAccount` 在恢复归档账户时也调用 `catchUpAutoPosted`，并不只有应用启动会触发。新方案须统一入口，使其符合用户确认的下次启动处理规则，同时避免绕过恢复确认与币种资格检查。
- 用户曾选择对无法区分类型的旧账单保持手动并确认；后续明确不考虑旧数据兼容性，该旧数据处理方案不再属于本次范围。
- 用户确认：关闭某类自动入账开关时，已经到期但尚未入账的该类账单转为手动处理，即使以后再次开启也不自动补记。
- 用户曾选择在旧账单详情中确认无法判断的类型；该旧数据场景已按用户后续要求移出本次范围。
- 用户确认：自动入账与账单提醒相互独立；开启自动入账后仍按账单自己的提醒设置发送。非当前币种提醒暂停的规则仍适用。
- 用户补充：新建收支记录时选择“默认 / 计划 / 订阅 / 重复”，之后不能更改模式；用户认为因此不存在旧账单类型无法判断的情况。
- 用户还提出可由用户选择“仅这一期 / 这一期和之后 / 所有排期”的作用域；后续确认这些作用域只针对普通账单字段。
- 用户进一步确认：三个作用域仅用于金额、日期等普通字段；创建后模式始终不可更改。
- 用户要求更改数据库结构，以保存新账单的表单模式；明确没有需要保留的旧数据，不考虑旧数据兼容性。
- 代码核对：当前模式是表现层枚举，`recurring_series` 没有模式列；新模型需要明确持久化模式，但不需要根据旧排期字段反推原模式。
- 用户确认：计划、订阅或重复账单入账后按普通交易展示和导出，不要求保留并识别来源模式。已入账交易仍需支持正常的事件重放与备份。
- 当前存储的 `autoPost` 表示原订阅行为，不能直接当成将来三类全局开关的值；新模型需持久化所选模式，而不能依靠排期形状反推。旧数据类型恢复不在本次范围。
- 用户最新确认：全局开关只属于本机设置，不写入备份；恢复保留目标设备开关，新安装默认关闭。账单资格与待确认批次仍写入备份。
- 用户确认：恢复时目标设备的开关已经关闭，备份中该类型既有待确认批次保留，开启后询问；其他未入账的逾期账单转为手动。恢复后用户主动关闭开关时，仍按原规则将该类型待确认逾期账单转手动。
- 若允许用户反复开关并保证关闭期间到期的实例以后不被自动补记，仅保存每类当前开关的布尔值不足以独立证明历史实例资格；需要连同币种切换边界、未物化期次、备份恢复和中断重试一起设计持久化判定依据。具体建模方式尚未确定。
- 当前用户偏好写入 SharedPreferences，系列和实例则在 SQLite。若开关切换与“已到期实例转手动”的资格边界分开落盘，中途崩溃可能只完成其中一半；方案需提供原子持久化或可验证的恢复协议。备份须保存资格但排除本机开关，恢复时与本机设置协调，不能只靠界面先后调用。
- 当前 `TransactionRecorded` 事件没有原始表单模式；用户已明确入账后按普通交易展示和导出，不要求识别来源模式。无需仅为展示来源而增加事件模式字段；普通交易仍须保持可重放。

## Answer

- “自动入账”是在应用账本中生成交易，不涉及银行扣款。计划、订阅、重复各有一个全局开关，初始全部关闭，对相应类型的现有与未来账单生效。
- 开关仅存本机，不包含在备份中；恢复不会覆盖本机开关，账单资格和待确认批次则随备份保留。
- 恢复到开关已关闭的设备时，既有待确认批次保留至开启后询问，其他未入账逾期账单转为手动；这与恢复后主动关闭开关的规则不同。
- 创建时持久化所选模式，之后不可变；普通字段仍可按现有三个作用域修改。入账交易按普通交易展示与导出，无须展示来源模式。不考虑新模型上线前的数据兼容。
- 开关关闭期间到期的账单保持手动；关闭时已到期未入账的账单也转为手动。之后开启只对开启后到期且仍符合其他条件的账单生效，不追溯补记。
- 一般自动入账按下次启动机制执行；用户同意恢复确认时可处理该确认批次。提醒与开关独立，但成功入账后取消尚未触发的提醒。非当前币种暂停自动入账和提醒；币种切换及恢复待确认批次的例外按[账单与通知](11-recurring-notifications.md)和[备份恢复](08-migration.md)处理。
- 永久手动资格不会因为重新开启、重启、单期改期或普通字段编辑而恢复。具体持久化、未物化期次、切换中断及账单恢复的原子协议在关联工程票据中验证。
