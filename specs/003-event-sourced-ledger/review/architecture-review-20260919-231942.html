Six deepening opportunities

The migration landed. This review asks a different question: now that DDD + Feature First + CQRS + Event Sourcing are in, are the seams in the right place? Everything below is read off the working tree — file and line, not directory names.

Holds up
  • One projection writer, one balance point
  • Append + project in one transaction
  • Money as int minor units, end to end
  • Write-time category snapshots
Shallow
  • 7 interfaces, 1 adapter each, 0 fakes
  • All 9 LedgerService methods forward
  • 1 dead interface, 4 dead repository methods
Leaks
  • Aggregate runs only at apply time
  • Projection depends on wall clock
  • balanceMinor means two things

Method: 4 parallel code scans (write chain / read+projection / shallow modules / presentation+boundaries), git churn over 79 commits, and first-hand reads of every file cited. No CONTEXT.md or docs/adr/ exists — the decision record is specs/003-event-sourced-ledger/.

candidate 01

The aggregate never runs on the write path

Strong
Files
domain/model/transaction.dart domain/commands/record_transaction_command.dart domain/commands/correct_transaction_command.dart data/projections/ledger_projector.dart
Problem

Transaction is documented as the aggregate root and owns nine invariant checks in validate(). It is constructed in exactly one place — inside the projector, at apply time. No command ever builds one. The validated local is dead the instant it is checked. 

// ledger_projector.dart:231-244
final txn = Transaction(...);
final violation = txn.validate();
if (violation != null) {
  throw StateError('...violates invariants: $violation');
}
// 'txn' is never read again — every later
// line uses 'p' (the raw payload)
// transaction.dart:66-71 (doc comment)
/// Aggregate root. Invariants (validated
/// in [Transaction.validate]):
/// - postings is non-empty,
/// - income/expense have exactly 1 posting,
/// - transfer has exactly 2 postings ...
// ...but the write path never calls it

So the same rules get re-typed at the command layer, and some land in three places:

rulesitesnote
amount > 03UI + command + aggregate
transfer: same account2command :128 & aggregate :111
transfer: same currency2command :153 & aggregate :112
kind → CategoryType42 commands, repo, reports DAO
kind → PostingDirection32 commands + aggregate
category type matches kind2 of 3missing from convert_scheduled_to_posted

That last row is the real cost. There are three writers of TransactionRecorded, and one of them skips a rule the other two enforce. Because the aggregate isn't a gate, nothing catches it — and when the projector does throw, guard() maps a non-CommandRejected error to LedgerErrorCode.unknownEvent, so an invariant violation reaches the user as a generic unknown-event failure.

Before / After
BEFORE — validate() sits after the seam
1 form screen
2 view model (mints commandId)
3 LedgerService (forwards)
4 command re-types the rules
5 envelope → store → commit point
6 projector → Transaction.validate() ← too late; throw = rollback

Rules live in 4 places. A miss is found by a rollback, not by the writer.

AFTER — the aggregate gates every writer
1 command builds Transaction
2 validate() → reject before any event exists
3 envelope from the validated aggregate
4 store → commit point
5 projector validates again (replay guard, now redundant-by-design)

Shape rules in one place; commands keep only context rules (exists / not archived).

Deletion test

Delete Transaction and the complexity reappears — replay still needs shape checks. So it earns its keep as a checker. What does not exist is any gate on the write side; that is the deepening, and it is additive, not a rewrite.

Benefits
  • Locality — a new invariant is one edit, in the aggregate.
  • Leverage — one gate covers 11 command files.
  • Testability — invariant tests stop needing a DB + projector; the aggregate is testable through its own interface.
  • AI navigability — "where are transaction rules?" gets one answer.
candidate 02

Monthly snapshots depend on the wall clock — the rebuild is not reproducible

Strong
Files
data/projections/monthly_snapshot_projector.dart data/projections/ledger_projector.dart core/domain/clock/clock.dart test/.../projection_rebuild_equivalence_test.dart
Problem

DomainClock exists precisely for this, with a FixedClock ready to go. The snapshot projector takes one — and no caller in the codebase ever passes it. Production, the test harness, and the service test all build LedgerProjectorImpl(db), which constructs the snapshot projector with the default SystemClock(). 

// ledger_projector.dart:35-36
late final MonthlySnapshotProjectorImpl _snapshots =
    MonthlySnapshotProjectorImpl(_db);   // no clock

// every construction site:
//   ledger_projector.dart:366  (provider)
//   ledger_service_harness.dart:73
//   ledger_service_test.dart:56
// — none of them inject one
// monthly_snapshot_projector.dart
:109  anchorMonth ??= _monthOf(_clock.today());
:112  var latest = _monthOf(_clock.today());
:183  updatedAt: Value(_clock.now()),

// :112 decides how many snapshot rows
// get written (:186-188 walks forward
// month by month until reaching latest)

Line 112 is the load-bearing one: the set of rows produced depends on which day the rebuild runs. Rebuild a ledger in January and again in March and you get different projections from the same events.

This contradicts the project's own constitution

Constitution VII (Event Sourcing Governance) requires projections be "reproducible field-for-field from the event store alone (golden equivalence tests gate this)". The golden test passes only because it rebuilds immediately after writing, and because its comparison deliberately drops the artifacts the clock controls — id / createdAt / updatedAt are excluded from capture().

The exclusion list is the tell: it is exactly the surface the un-injected clock writes to.

A related leak: clock.dart's doc says "Commands must never call DateTime.now() directly" — but envelopeFor() calls it for occurredAt and recordedAt, and none of its 13 call sites passes occurredAt. So every envelope stores the write wall-clock while the payload stores the business date, and consumers disagree about which one to read.

Before / After
BEFORE — same events, two rebuilds, two truths
rebuild on 2026-01-31
rows: 2025-11, 2025-12, 2026-01
rebuild on 2026-03-31 — identical event store
rows: 2025-11 … 2026-03 (+2 rows)
Golden test green only because it excludes id/createdAt/updatedAt.
AFTER — clock at the seam
production
LedgerProjectorImpl(db, clock: SystemClock())
tests
LedgerProjectorImpl(db, clock: FixedClock(...))
Rebuild output becomes a pure function of the event store; the exclusion list can shrink.
Deletion test

Not applicable — the module earns its keep; the dependency is what is misplaced. The fix is to route the clock through the existing seam rather than create a new one.

Benefits
  • Testability — snapshot tests stop reading DateTime.now().
  • Correctness — closed months stop mutating on later rebuilds.
  • Locality — one injected dependency, already written.

Half the domain model has no caller outside tests

The single Transaction + Postings model is the migration's headline decision, and it buys income / expense / transfer in one shape. But transfers cannot be created from the app: the type selector offers two segments, and addTransaction requires a non-null categoryId, so it structurally cannot express one. candidate 06

Snapshot maintenance is orchestrated from inside the projector's switch

Worth exploring
Files
data/projections/ledger_projector.dart data/projections/monthly_snapshot_projector.dart
Problem

"Which events move a balance" is knowledge split across two modules. The projector's switch encodes it by calling the snapshot projector inline from four separate branches, and applyAll is a bare loop with no chance to coalesce. 

// ledger_projector.dart — four inline refresh sites
:58      await _snapshots.refreshAccount(p.accountId);          // AccountCreated
:72      await _snapshots.refreshAccount(p.accountId);          // OpeningBalanceSet
:76-78   for (final posting in p.postings) {
           await _snapshots.refreshAccount(posting.accountId);  // once per posting
         }
:82-84   for (final accountId in affected) {
           await _snapshots.refreshAccount(accountId);          // once per reversed account
         }

// :42-46 — no post-apply hook to hang a single refresh on
Future<void> applyAll(List<EventEnvelope> events) async {
  for (final event in events) { await apply(event); }
}

Each refresh in turn does eventsDao.getAll() — a full event-store scan. Creating an account emits two events under one command, so it scans twice; during rebuild this compounds into the O(events²) the code already flags in a ponytail comment. The cost is accepted; the placement is the issue — the projector knows which events matter, the snapshot projector knows how to recompute, and neither owns the decision to refresh.

One ordering detail worth noting while here: the reversal branch iterates a Set<String> built from rows fetched without an orderBy, so the refresh order is decided by unspecified SQL row order. It happens not to matter today, which is exactly the kind of thing that stops being true later.

Delete MonthlySnapshotProjector → the anchor/chain logic re-forms nowhere; it earns its keep. The orchestration is the shallow part: it is a 4-line convention repeated in a switch, and the fix concentrates it.

Benefits
  • Locality — a new event type cannot forget to refresh.
  • Efficiency — natural place to coalesce scans.
  • Testability — the refresh contract becomes assertable on its own.

Worth keeping — do not "simplify" these

The append hook is the best seam in the codebase

AppendOptions(apply:) makes write-and-project atomic and lets rebuild reuse the identical apply path. One seam, two consumers. That is why the golden-equivalence test can exist at all.

DriftEventStore is genuinely deep

Transaction boundary, two-phase batch pre-check (so multi-event commands don't self-collide), GSN assignment, projector hook, paging arithmetic — all behind five methods. It is not a DAO wrapper.

One sign convention, one balance writer

Posting.signedImpact and the projector as sole balanceMinor author both hold — the one exception (postingSignedImpact in the DAO) is a projection-row re-implementation worth folding back, not a design failure.

Money as int minor units, end to end

Money.fromDouble is the single double→int bridge, at the input boundary. A repo-wide grep finds no floating-point arithmetic on any accounting path.

The risk-mapped regression suite

ledger_invariants_test, monthly_snapshot_test, projection_rebuild_equivalence_test — named after the spec's twelve financial risks rather than after classes. That is unusually good, and it is the reason several findings above are provably contained rather than merely suspected.

Write-time category snapshots

Copying name/icon/color onto the transaction row means archival never distorts history, with no join to the live table. It closes risk #8 permanently.

Also surfaced — not carded, but load-bearing

Accounts and categories have no single owner

Entity, repo interface+impl, DAO and table live in lib/core; commands, queries and services in features/settings; the events and every projector handler in features/ledger. Both feature layers rebuild AccountEntity/CategoryEntity from projection rows themselves, and the reports widget goes further — it fabricates a synthetic CategoryEntity(id: 'others') in the UI. Feature First is intact as a directory rule; it does not match the domain boundary, because "account/category management" is a feature in the UI and an aggregate in the ledger.

Domain → data imports, in every command file

Class-level dependencies are clean (commands hold EventStore, an interface). But because the @riverpod provider lives in the same file, ~20 domain files import drift_event_store.dart and ledger_projector.dart directly. The file-level dependency is what leaks; the convention is what causes it.

Existence checks use two different sources

Most commands read the projection to confirm an account exists; rename_account and archive_account instead ask the event stream (readStream(id).isNotEmpty). Same rule, two truths, and the event-store variant is stricter than the projection one.

Dead surface inventory

ProjectionCursor (0 impls, 0 refs) · LedgerRepository ×4 methods · MonthlySnapshotDao.watchAllForMonth · EventStore.commandExists (0 prod callers) · RecurringDao.saveSeries (0 prod callers) · ReportsRepository.watchHeatmapData/…AmountData (identical) · account_summary_card.dart (whole widget) · insert_or_update_scheduled + project_recurring_events providers (0 callers)

A second composition root

LedgerServiceHarness hand-wires ~110 lines of the same graph Riverpod builds, so every constructor change must land twice. Its seedAccount also inserts projection rows directly with lastUpdatedEventId: 0 — a state production cannot reach, and one rebuild would erase.

Top recommendation

Start with candidate 01 — put the aggregate on the write path

It is the one finding that is simultaneously a DDD correctness issue, a locality problem, and the root cause of four separate duplication rows in its own table. Every other candidate is either downstream of it or independent of it; none of them unblock it. The fix is additive — commands already build the postings, they simply never wrap them in the aggregate they are supposed to be producing — so it can land writer by writer without a freeze.

Ship first if you want a quick win

Candidate 02. Injecting the clock is a one-line change at a seam that already exists, and it removes a live contradiction with the constitution's determinism rule.

Ship first if correctness outranks design

Candidate 03. Two meanings behind one field name is the only finding here that can put a wrong number in front of a user without anyone noticing.

Answer before the others

Candidate 05 is a scope question, not a refactor. "Is transfer shipping?" changes whether the rest of the transfer branch is leverage or dead weight.
